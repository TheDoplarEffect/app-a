# Round 1 — Architecture review: abstractability & design patterns

**Repo:** `/home/dev/app-a` (Kotlin, programmatic Views, minSdk 26 / target 35)
**Lens:** tokens→atoms→screens layering, god-objects, testability/injection of LiveRepository & Clients, over/under-engineering.
**Scope:** `app/src/main/java/com/example/appa/*.kt` (+ `MainActivity.java`, manifest), `app/src/test`.

## References consulted (cited by name)

- **Android Architecture Guide** — https://developer.android.com/topic/architecture — principles: *"Separation of concerns"* ("It's a common mistake to write all your code in an `Activity`"; "don't entrust [app] state to UI components"), *"Single source of truth (SSOT)"* (only the SSOT may mutate a data type), *"Unidirectional data flow (UDF)"* (state flows down, events flow up, state updated in one place), and the **UI / Data / Domain layer** model.
- **Android Data-layer guide** — https://developer.android.com/topic/architecture/data-layer — *"each repository defines a single source of truth"*; *"other layers should never access data sources directly; the entry points to the data layer are always the repository classes"*; repositories *"combine different data sources and solve any potential conflicts between the data sources"*.
- **Clean Architecture** (Robert C. Martin, *Clean Architecture*, 2017) — the **Dependency Rule** ("source code dependencies can only point inwards"; inner circles know nothing about outer circles), the Entities → Use Cases → Interface Adapters → Frameworks & Drivers rings, and **dependency inversion** at boundaries (interfaces owned by the inner layer).
- **SOLID** — SRP, OCP, DIP in particular.

## Verdict

The **inner/domain layer is genuinely clean-architecture-shaped**: `Tokens.kt`, `Catalog.kt`, `PagerMath.kt`, `Config.kt`, `Http.kt`, `Clients.kt` are pure JVM Kotlin with zero Android imports and are unit-tested (`DesignTokensTest`, `CatalogTest`, `PagerMathTest`, `RequestStoreCoreTest`, `LiveParsingTest`), and the network clients are properly constructor-injected with `HttpTransport`. The problems start exactly where Clean Architecture draws the first boundary: everything above the domain (the `AppState` global, the screens, and even one atom) bypasses abstractions and reaches for concrete globals — no repository interface, no UDF/state holder, and the atom layer leaks app state. Details below.

## Findings

### High

- **H1 — `AppState` is a god-object / service locator that every layer depends on concretely.** `AppState.kt:6-45` is a global mutable `object` exposing `store`, `config`, nullable `repo`, plus behavior (`init`, `saveConfig`, `requestFor`, `mediaById`); 47 call sites across all 5 screens (`MainScreen.kt`, `DetailActivity.kt`, `RequestsActivity.kt`, `SettingsActivity.kt`, and even `Components.kt:459`). This violates the Dependency Rule (UI layer depends on a concrete global, not an abstraction — DIP) and the guide's *separation of concerns* / *SSOT*: conflict resolution between live and placeholder data is hidden inside `AppState.mediaById` (`AppState.kt:45`, `repo?.mediaById(id) ?: Catalog.byId[id]`) instead of in a repository, which the data-layer guide explicitly assigns to repositories. **Fix:** introduce `interface MediaRepository { fun browse(type): List<Media>; fun search(q): List<Media>; fun details(m): Media; fun magnetsFor(m): List<Magnet>; fun request(m): String; fun refreshStatuses(store): List<Request>; fun mediaById(id): Media? }` with two implementations — `PlaceholderRepository` (delegates to `Catalog`) and `LiveRepository` — and make `AppState.repo: MediaRepository` **non-null**. Reduce `AppState` to a composition root (Clean Architecture's "main"): it only wires `store`/`repo`/`config` in `init()`; screens receive them via constructor instead of reading the global.

- **H2 — Nullable `repo` + six `!!` call sites instead of polymorphism (OCP).** `AppState.repo: LiveRepository?` (`AppState.kt:16-17`) forces `AppState.repo!!` at `MainScreen.kt:179,203` and `DetailActivity.kt:95,190,210,244`, each wrapped in ad-hoc `runCatching`. A null-check standing in for "placeholder vs live" is the textbook OCP violation. **Fix:** with H1's non-null `MediaRepository`, `PlaceholderRepository` implements the same surface over `Catalog` (browse = `Catalog.ofType`, magnets = `Catalog.magnetsByMediaId`, request = local-only), so `liveMode` becomes a property of the chosen implementation and all `!!`/`runCatching` wrappers at call sites disappear.

- **H3 — No UDF / state holder: screens are the state holder, the thread owner, and the cache.** `MainScreen.kt:24-41` keeps `itemsByTab`, `loadedAt`, `searchCache`, `signatureByTab` as private mutable maps and runs `Thread { … handler.post { … } }` inline (`MainScreen.kt:44-67` ticker, `165-211` `loadItems`); `DetailActivity.doRequest` (`DetailActivity.kt:184-201`) mutates the store on a raw thread then calls `recreate()` to re-render. This is precisely the "all your code in an Activity" anti-pattern the guide names, and it breaks UDF (state flows down / events flow up, one place mutates state). **Fix:** extract a plain-Kotlin, JVM-testable state holder per screen, e.g. `class MainStateHolder(repo, store) { var state = MainUiState(...); fun onEvent(e: MainEvent) }` with `MainEvent` sealed class (`TabSelected`, `QueryChanged`); the screen only renders `state` and forwards events. Replace `recreate()` in `DetailActivity` with re-rendering the actions row (the diff-render pattern already used in `MainScreen.renderCurrent`).

- **H4 — `LiveRepository`'s constructor performs blocking network I/O, on the main thread.** `LiveRepository.kt:51-55` (`init { … prowlarr.indexerIdByName("audiobook") … }`) does a synchronous HTTP call during construction, and `AppState.init`/`saveConfig` construct `LiveRepository` on the calling thread (`AppState.kt:29,38`) — which is the main thread, since every Activity's `onCreate` calls `AppState.init` (`MainScreen.kt:66`, `DetailActivity.kt:31`, `RequestsActivity.kt:27`, `SettingsActivity.kt:24`). With a configured Prowlarr this blocks the UI thread for up to the 25 s connect timeout (`Http.kt:24`) → ANR. It also makes the class surprising to construct in tests. **Fix:** make it lazy like the other clients: `private val audiobookIndexerIds: String by lazy { if (cfgN.hasProwlarr) prowlarr.indexerIdByName("audiobook")?.toString() ?: "" else "" }` (mirrors `LiveRepository.kt:40-43`).

### Medium

- **M1 — The atom layer reaches into `AppState` (layering violation).** `PosterCard` calls `AppState.requestFor(m.id)` directly (`Components.kt:459`), contradicting the file's own contract ("components … expose only semantic parameters", `Components.kt:24-31`) and making an atom untestable/unreusable without the global initialized. **Fix:** add `status: RequestStatus? = null` parameter to `PosterCard` and pass it from `MainScreen.renderCurrent` (`MainScreen.kt:231`, which already computes `AppState.requestFor(it.id)?.status` for the signature at `MainScreen.kt:220`).

- **M2 — Media has no single source of truth; `LiveRepository.mediaCache` is an unsynchronized second source.** `private var mediaCache` (`LiveRepository.kt:180`) is a plain `MutableMap` written from the main thread (`remember`, `markAvailability`, `LiveRepository.kt:182,189-198`) and read/mutated from the ticker's background thread (`refreshStatuses`, `LiveRepository.kt:138-176`) — a data race; and `AppState.mediaById` (`AppState.kt:45`) merges it with `Catalog.byId`, duplicating the repo's own fallback (`LiveRepository.kt:183`). Per the data-layer guide, the repository — not `AppState` — should own combining sources. **Fix:** wrap the media lookup in a single `MediaRepository` (H1) whose `mediaById` does the live-cache-then-catalog fallback; make the cache a `ConcurrentHashMap` or guard it with the same lock style as `RequestStoreCore` (`Catalog.kt:98`).

- **M3 — Tokens→atoms→screens is leaky: raw values bypass the tokens.** Despite Tokens.kt's promise "components never hard-code values" (`Tokens.kt:11-12`), there are hard-coded colors (`0xB3000000` rating/scrim chips at `Components.kt:455`, `DetailActivity.kt:79-80`; `Chip` default fg `0xFFFFFFFF` at `Components.kt:337`; `Color.WHITE` + alphas 0.85/0.08 in `GradientPoster`, `Components.kt:390-406`) and dozens of raw `dp(...)` sizes/margins in atoms and screens (`Components.kt:143,151,181,234,251,296,442,454`; `DetailActivity.kt:59,72,81`; `RequestsActivity.kt:102,116`; `roundedClip(12)` at `RequestsActivity.kt:103,107`). **Fix:** add a component/size token group to `DesignTokens` (e.g. `sizes.buttonDp=40, posterMinDp=150, thumbW/H=44/64, heroDp=300, scrimDp=56`, `colors.chipScrim=0xB3000000`, text-on-poster = `textOnAccent`) and replace the literals; the existing `DesignTokensTest` invariant style can pin them.

- **M4 — Two parallel magnet models.** `Catalog.Magnet` (`Catalog.kt:48`) vs `LiveMagnet` (`LiveRepository.kt:11-19`), manually converted in `DetailActivity.kt:218-221`. **Fix:** keep one domain `Magnet` (in `Catalog.kt` next to `Media`) with optional live-only fields (`downloadUrl`), delete `LiveMagnet`, and have `LiveRepository.magnetsFor` return `List<Magnet>`.

- **M5 — Duplicated polling/ticker logic in two screens.** `MainScreen.kt:44-67` and `RequestsActivity.kt:57-77` both hand-roll `store.tick()` + `Thread { repo?.refreshStatuses(store) }` + `handler.post` + `postDelayed(5s/1s)`. **Fix:** one small `StatusPoller(handler, store, repo, onChanged: () -> Unit)` started/stopped with the screen lifecycle; both screens just subscribe.

- **M6 — Ticker is never cancelled (no teardown path).** `MainScreen.attach()` posts the ticker (`MainScreen.kt:123`) but `MainScreen` has no `detach()` and `MainActivity.java` has no `onDestroy` hook — the runnable keeps firing (and calling `repo.refreshStatuses`) after the activity is destroyed. **Fix:** add `fun detach() { handler.removeCallbacks(ticker) }` to `MainScreen` and call it from `MainActivity.onDestroy`.

### Low

- **L1 — `pingAll()`'s Prowlarr check is hard-coded to `true`** (`LiveRepository.kt:59`: `runCatching { prowlarr.search("test", "").isNotEmpty() || true }`), so Settings' "Test connection" always shows Prowlarr ✓. **Fix:** `runCatching { prowlarr.search("test", "") }.isSuccess`, or call `/api/v1/indexer/status`.
- **L2 — Runtime theme swap is not actually honored end-to-end.** Tokens.kt advertises "swap at runtime" (`Tokens.kt:174-178`), but screens capture `val t = AppTheme.current` once (`MainScreen.kt:64`, `DetailActivity.kt:30`, `SettingsActivity.kt:22`) while `BottomNavBar.select` re-reads `AppTheme.current` mid-animation (`Components.kt:265,272`) — inconsistent policy. Related: debounce `350` ms hard-coded (`Components.kt:321`) and aurora `24_000` ms + alpha `52` hard-coded (`AuroraBackground.kt:57,96`) instead of `MotionTokens`/color tokens. **Fix:** add `motion.debounceMs` and `motion.auroraDurationMs` tokens; pick one policy (capture-at-build) and use the captured `t` everywhere.
- **L3 — Dead code (over-engineering residue):** unused `glassDrawable` (`Glass.kt:18`), `crossfadeOut` (`Motion.kt:102`), `LinearOutSlowIn` (`Motion.kt:24`), `Context.dpF`/`Context.sp` (`Density.kt:10-11`), `SwipePager.pageView` (`SwipePager.kt:31`), `AuroraBackground.renderOnce` (`AuroraBackground.kt:99`). **Fix:** delete them.
- **L4 — `Skeleton`'s infinite `ValueAnimator` is never cancelled** (`Components.kt:512-530`); it keeps animating a detached view. **Fix:** cancel in `onDetachedFromWindow` (attach an `AnimatorListener` or use a `View`-scoped animator).

## Clean areas (one-liners)

- **Inner/domain layer honors the Dependency Rule:** `Tokens.kt`, `Catalog.kt` (`StatusRules`, `RequestStoreCore`, `Catalog`), `PagerMath.kt`, `Config.kt`, `Http.kt`, `Clients.kt` contain no Android imports and are covered by the five JVM test classes — exactly Martin's "inner circles know nothing about outer layers".
- **Clients and `LiveRepository` are properly injectable:** every client takes `HttpTransport = realHttp` (`Clients.kt:46,118,167,201,266,313`; `LiveRepository.kt:36`) and `LiveParsingTest` drives them with a fake transport (`LiveParsingTest.kt:311,327`) — correct DIP at the data-layer boundary; `ImageLoader` is the exception (raw `URL(url).openStream()`, `ImageLoader.kt:34`, no transport/timeout injection) but it is peripheral.
- **`RequestStoreCore` is a proper single source of truth for requests** with injected `load`/`save` lambdas and a lock (`Catalog.kt:92-99,135`) — matches the guide's SSOT principle and is tested (`RequestStoreCoreTest`).
- **The tokens→atoms→screens layering is honored in the common path:** atoms take `t: DesignTokens = AppTheme.current` and read only token fields, and `DesignTokensTest` pins scale/contrast invariants; the violations are the specific leaks listed in M1/M3, not the pattern itself.
